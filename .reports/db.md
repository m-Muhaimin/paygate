## 3. Function signatures (`20261013000003_functions.sql`, `20261013000004_rls.sql`)

All `SECURITY DEFINER`, `SET search_path = public`.

```sql
assign_wallet(p_provider text, p_merchant_id text) returns public.wallets
-- status='active' AND device.status='active' AND device.last_heartbeat_at > now() - interval '3 minutes'
-- AND today_total < daily_limit AND pending(created|awaiting_payment) count < concurrency_cap
-- ORDER BY last_assigned_at ASC NULLS FIRST LIMIT 1 FOR UPDATE SKIP LOCKED; sets last_assigned_at = now()
-- returns NULL when none qualify (map to 503 no_wallet_available)

claim_incoming_txn(p_provider text, p_trx_id text, p_wallet_id text, p_payment_id text) returns boolean
-- UPDATE incoming_txns SET claimed_payment_id = p_payment_id
--  WHERE provider=… AND trx_id=… AND wallet_id=… AND claimed_payment_id IS NULL  → RETURNING true
-- returns true only for the call that won the race, else false

merchant_balance(p_merchant_id text) returns bigint
-- + merchant_payable credits − merchant_payable debits − payout debits − refund debits

auth_merchant_id() returns text   -- RLS helper: auth.uid() → merchant_users.merchant_id (own merchant only)
```

**EXECUTE grants (Supabase security checklist):** `assign_wallet` / `claim_incoming_txn` / `merchant_balance` are `REVOKE`d from `PUBLIC, anon, authenticated` and granted to `service_role` only — they accept a merchant/tenant argument and must not be callable by end users (BOLA on `merchant_balance`). `auth_merchant_id()` is granted to `authenticated` (returns only the caller's own merchant; NULL for anon).

## 4. RLS

RLS enabled on all 14 tables. Policies `TO authenticated`, keyed on `merchant_id` via `(select public.auth_merchant_id())` (wrapped in SELECT per RLS-perf guidance; helper is `SECURITY DEFINER` to avoid the `merchant_users` → policy → helper recursion trap, 42P17):

| table | select | insert | update | delete |
|---|---|---|---|---|
| merchants (scoped by `id`) | ✓ | | ✓ | |
| pricing_plans | ✓ | ✓ | ✓ | ✓ |
| payments | ✓ | ✓ | ✓ | |
| payouts | ✓ | ✓ | | |
| device_pairing_codes | ✓ | ✓ | | |
| ledger_entries, settlements, webhook_deliveries, merchant_users, api_keys | ✓ | | | |

No policies (deny-by-default; `service_role` bypasses): `wallets`, `devices`, `audit_log` (admin fleet/audit); `incoming_txns` (**insert-only ingest from the device SMS webhook via `service_role`**, documented in-file).

Every UPDATE policy carries both `USING` and `WITH CHECK`. Data API grants are explicit (tables are **not** auto-exposed — changelog 2026-04-28, enforced 2026-10-30): `service_role` gets all; `authenticated` gets exactly the privileges its policies allow; `anon` gets nothing (public endpoints are server-side/service-role).

## 6. Deviations from SPEC / documented decisions

1. **`wallets.concurrency_cap` added** (integer NOT NULL default 20) — not in SPEC §6, but mandated by the brief's `assign_wallet` concurrency-cap requirement.
2. **`wallets` / `devices` have no `merchant_id`** — SPEC §6 omits it; they are treated as a platform-wide fleet (admin-managed, SPEC §7). Consequence: RLS is enabled but they are `service_role`-only (no merchant policies). `assign_wallet`'s `p_merchant_id` is accepted for signature stability but currently unused (reserved for future per-merchant scoping).
3. **`incoming_txns` has no `id` column** — SPEC §6 gives composite PK `(provider,trx_id,wallet_id)`; the documented `itx_` prefix is therefore unused.
4. **`merchant_users.id` prefix `mru_`** — the SPEC prefix list does not cover `merchant_users`; `mru_` was chosen and documented.
5. **`merchant_users.auth_user_id` is NOT FK-constrained to `auth.users`** — so the seed can create a merchant user without creating an Auth user. Validate/resolve against `auth.users` in the app; add the FK later if desired.
6. **`devices.token_hash` nullable** — a device row can exist before pairing completes; SPEC implies it is required, so treat "has token_hash" as the authenticated-state check.
7. **`pricing_plans.amount` nullable** — required only when `open_amount = false` (enforced by the consistency check), since SPEC lists `open_amount`/`min_amount`/`max_amount` alongside `amount`.
8. **Inferred enum values not enumerated in SPEC:** `merchant_status` (pending/active/suspended), `kyb_status` (pending/under_review/approved/rejected), `risk_tier` (low/medium/high), `settlement_status` (pending/processing/paid). Change here before downstream code depends on them if a different set is intended.
9. **`payments.idempotency_key` uniqueness is a partial unique index** (`where idempotency_key is not null`) — required because NULLs must not collide. This is the tenant-scoped idempotency key (`merchant_id, idempotency_key`).
10. **`config.toml` has no `region` key** — the Supabase CLI config has no region field; region is a hosted project attribute. `ap-southeast-1` is documented as a comment next to `project_id = "paygate"`.
11. **RLS write matrix is narrower than "full CRUD"** — ledger/settlements/webhook_deliveries/api_keys are SELECT-only for `authenticated` (system-generated / server-managed). App writes go through `service_role`. Widen if the dashboard must write these directly.
12. **`audit_log."before"` / `"after"` are quoted** (reserved-ish identifiers); reference them as `before`/`after` via PostgREST.
